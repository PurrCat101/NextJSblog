# ความรู้เกี่ยวกับการทดสอบซอฟต์แวร์

Error, Bug, Fault, Failure

- **Error**: เป็นความผิดพลาดที่เกิดจากการเขียนโค้ดหรือการออกแบบที่ไม่ถูกต้อง เช่น การใช้ตัวแปรที่ไม่ได้ประกาศ
- **Bug**: เป็นข้อบกพร่องในซอฟต์แวร์ที่ทำให้โปรแกรมทำงานไม่ถูกต้อง เช่น โปรแกรมค้างเมื่อผู้ใช้คลิกปุ่ม
- **Fault**: เป็นสาเหตุของการเกิด bug ซึ่งอาจเกิดจากการเขียนโค้ดที่ไม่ถูกต้องหรือการออกแบบที่ไม่ดี
- **Failure**: เป็นผลลัพธ์ที่เกิดจาก fault ซึ่งทำให้ระบบไม่ทำงานตามที่คาดหวัง เช่น ระบบไม่สามารถประมวลผลข้อมูลได้

**ตัวอย่าง**: หากมีการเขียนฟังก์ชันที่คำนวณผลรวมของตัวเลข แต่มีการใช้ตัวแปรที่ไม่ได้ประกาศ (Error) จะทำให้เกิด bug ในโปรแกรม ซึ่งอาจนำไปสู่การคำนวณที่ผิดพลาด (Fault) และสุดท้ายทำให้โปรแกรมไม่สามารถแสดงผลลัพธ์ได้ (Failure)

## Software Development Lifecycle (SDLC)

SDLC คือกระบวนการที่ใช้ในการพัฒนาซอฟต์แวร์ ซึ่งประกอบด้วยขั้นตอนต่างๆ เช่น:

- **Planning**: การวางแผนและกำหนดความต้องการ
- **Analysis**: การวิเคราะห์ความต้องการและข้อกำหนด
- **Design**: การออกแบบระบบ
- **Implementation**: การพัฒนาและเขียนโค้ด
- **Testing**: การทดสอบซอฟต์แวร์
- **Deployment**: การนำซอฟต์แวร์ไปใช้งาน
- **Maintenance**: การบำรุงรักษาและปรับปรุงซอฟต์แวร์

**ตัวอย่าง**: ในการพัฒนาแอปพลิเคชันมือถือ ทีมงานจะเริ่มจากการวางแผนฟีเจอร์ที่ต้องการ (Planning) จากนั้นจะทำการวิเคราะห์ความต้องการของผู้ใช้ (Analysis) และออกแบบ UI/UX (Design) ก่อนที่จะเริ่มเขียนโค้ด (Implementation) และทดสอบแอปพลิเคชัน (Testing)

## Testing Lifecycle

Testing Lifecycle คือกระบวนการที่ใช้ในการทดสอบซอฟต์แวร์ ซึ่งประกอบด้วยขั้นตอนต่างๆ เช่น:

- **Requirement Analysis**: วิเคราะห์ความต้องการในการทดสอบ
- **Test Planning**: วางแผนการทดสอบ
- **Test Design**: ออกแบบกรณีทดสอบ
- **Test Execution**: ดำเนินการทดสอบ
- **Test Closure**: สรุปผลการทดสอบและจัดทำรายงาน

**ตัวอย่าง**: ในการทดสอบเว็บไซต์ ทีมงานจะเริ่มจากการวิเคราะห์ความต้องการในการทดสอบ (Requirement Analysis) จากนั้นจะวางแผนการทดสอบ (Test Planning) และออกแบบกรณีทดสอบ (Test Design) ก่อนที่จะดำเนินการทดสอบ (Test Execution)

## Testing Methodologies

Testing Methodologies คือแนวทางในการทดสอบซอฟต์แวร์ ซึ่งมีหลายประเภท เช่น:

- **Manual Testing**: การทดสอบด้วยมือ โดยผู้ทดสอบจะทำการทดสอบซอฟต์แวร์ด้วยตนเอง
- **Automated Testing**: การทดสอบโดยใช้เครื่องมืออัตโนมัติ เช่น Selenium
- **Black Box Testing**: การทดสอบที่ไม่สนใจโค้ดภายใน แต่จะทดสอบจากผลลัพธ์ที่ได้
- **White Box Testing**: การทดสอบที่สนใจโค้ดภายในและโครงสร้างของโปรแกรม

**ตัวอย่าง**: ในการทดสอบแอปพลิเคชันมือถือ ทีมงานอาจใช้การทดสอบแบบ Manual เพื่อทดสอบ UI และการทำงานของฟีเจอร์ต่างๆ ขณะเดียวกันก็ใช้ Automated Testing เพื่อทดสอบฟังก์ชันการทำงานที่ซ้ำซาก

## Testing Levels

Testing Levels คือระดับของการทดสอบซอฟต์แวร์ ซึ่งประกอบด้วย:

- **Unit Testing**: การทดสอบหน่วยเล็กๆ ของโค้ด เช่น ฟังก์ชัน
- **Integration Testing**: การทดสอบการทำงานร่วมกันของหลายหน่วย
- **System Testing**: การทดสอบระบบทั้งหมด
- **Acceptance Testing**: การทดสอบเพื่อให้แน่ใจว่าซอฟต์แวร์ตรงตามความต้องการของผู้ใช้

**ตัวอย่าง**: ในการพัฒนาเว็บไซต์ ทีมงานอาจเริ่มจากการทดสอบฟังก์ชันการเข้าสู่ระบบ (Unit Testing) จากนั้นทดสอบการทำงานร่วมกันระหว่างฟังก์ชัน (Integration Testing) และสุดท้ายทดสอบเว็บไซต์ทั้งหมด (System Testing)

## Testing Pyramids

Testing Pyramids คือแนวทางในการจัดระเบียบการทดสอบซอฟต์แวร์ โดยแบ่งออกเป็นสามระดับ:

- **Unit Tests**: จำนวนมากที่สุดที่ทดสอบฟังก์ชันเล็กๆ
- **Integration Tests**: จำนวนกลางที่ทดสอบการทำงานร่วมกัน
- **End-to-End Tests**: จำนวนที่น้อยที่สุดที่ทดสอบระบบทั้งหมด

**ตัวอย่าง**: ในการพัฒนาแอปพลิเคชัน ทีมงานอาจมี Unit Tests จำนวนมากเพื่อทดสอบฟังก์ชันต่างๆ และมี End-to-End Tests เพียงไม่กี่กรณีเพื่อทดสอบการทำงานของแอปพลิเคชันทั้งหมด

## Performance Testing

Performance Testing คือการทดสอบเพื่อประเมินประสิทธิภาพของซอฟต์แวร์ เช่น ความเร็ว ความสามารถในการรองรับผู้ใช้จำนวนมาก และการใช้ทรัพยากร

**ตัวอย่าง**: ทีมงานอาจใช้เครื่องมือเช่น JMeter เพื่อทดสอบว่าเว็บไซต์สามารถรองรับผู้ใช้ 1,000 คนพร้อมกันได้หรือไม่

## Security Testing

Security Testing คือการทดสอบเพื่อประเมินความปลอดภัยของซอฟต์แวร์ เช่น การตรวจสอบช่องโหว่และการป้องกันการโจมตี

**ตัวอย่าง**: ทีมงานอาจใช้เครื่องมือเช่น OWASP ZAP เพื่อตรวจสอบว่ามีช่องโหว่ที่สามารถถูกโจมตีได้หรือไม่

## Regression Testing

Regression Testing คือการทดสอบซอฟต์แวร์หลังจากมีการเปลี่ยนแปลง เช่น การแก้ไข bug หรือการเพิ่มฟีเจอร์ เพื่อให้แน่ใจว่าการเปลี่ยนแปลงไม่ทำให้ฟังก์ชันที่มีอยู่ทำงานผิดปกติ

**ตัวอย่าง**: หลังจากที่ทีมงานแก้ไข bug ในฟังก์ชันการค้นหา ทีมงานจะทำการทดสอบฟังก์ชันการค้นหาอีกครั้งเพื่อให้แน่ใจว่าทำงานได้ตามปกติ

## Writing Test Scenario and Test Cases

การเขียน Test Scenario และ Test Cases เป็นขั้นตอนสำคัญในการทดสอบซอฟต์แวร์:

- **Test Scenario**: เป็นคำอธิบายทั่วไปเกี่ยวกับสิ่งที่ต้องทดสอบ เช่น "ผู้ใช้สามารถลงทะเบียนได้"
- **Test Case**: เป็นรายละเอียดที่ชัดเจนเกี่ยวกับการทดสอบ เช่น "เมื่อผู้ใช้กรอกข้อมูลที่ถูกต้องและคลิกปุ่มลงทะเบียน ระบบจะต้องส่งอีเมลยืนยัน"

**ตัวอย่าง**: Test Scenario อาจเป็น "การเข้าสู่ระบบ" และ Test Case อาจระบุว่า "เมื่อผู้ใช้กรอกชื่อผู้ใช้และรหัสผ่านที่ถูกต้อง ระบบจะต้องนำผู้ใช้ไปยังหน้าแรก"

## Writing Testing Reports

การเขียน Testing Reports เป็นการสรุปผลการทดสอบซอฟต์แวร์ ซึ่งควรประกอบด้วย:

- **Summary**: สรุปผลการทดสอบ
- **Test Cases Executed**: รายการของ Test Cases ที่ดำเนินการ
- **Defects Found**: รายการของข้อบกพร่องที่พบ
- **Recommendations**: ข้อเสนอแนะแก่ทีมพัฒนา

**ตัวอย่าง**: รายงานการทดสอบอาจระบุว่า "การทดสอบเสร็จสิ้นโดยมี Test Cases 50 รายการที่ดำเนินการ พบข้อบกพร่อง 5 รายการ และแนะนำให้แก้ไขข้อบกพร่องก่อนการปล่อยซอฟต์แวร์"
